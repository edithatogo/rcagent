## Delivered interface

`tools.heaps.assemble_packet` accepts captured case/profile bytes, a mapping of
artifact paths to bytes, an explicit evaluation timestamp and optional detached
manifest/decision/status verification inputs. It returns preparation and review
dispositions, errors, output bytes and a status observation. The real subprocess
entry point is `python -m tools.heaps`; the
[usage guide](../../../evaluation/heaps/h4-usage.md) contains the complete
reproducible example. Exit codes are 0 for prepared, 2 for rejected and 3 for
empty/all-abstain.

The output includes a readable draft report, supplied chronology and action
register; normalised case/profile/mapping artifacts; unchanged source/template
bytes; raw ingress captures; a detached construction manifest; and separate
status and verification observations. A supplied decision is preserved verbatim.
The consumer performs no network, model or external submission operation.

## Admission and representation

The consumer rejects malformed UTF-8/JSON, BOMs, duplicate keys, nonfinite
numbers, unpaired surrogates, invalid integer substitutions, excessive nesting,
unsafe paths and oversized artifacts. It applies the existing canonical domain
validator before the shared renderer and supplements the missing shared
date-time checker with strict parsing of all consumed timestamp fields.

It resolves typed references by actual kind and exact case/revision/fingerprint,
checks source-family and local locator consistency, and verifies exact raw
artifact hashes and lengths. Every canonical source has an explicit availability
state. Supplied manifest inventories must be complete and internally consistent;
historical bytes cannot disappear because of their filenames or semantic JSON
equality.

The report keeps observations, accounts, inferences, hypotheses, proposed
findings and recommendations separate. Contrary evidence, alternative
explanations, participation gaps and disagreements, distinct time assertions,
source derivation and concurrent routes remain visible. Missing documentation
does not become a care-omission finding. Recommendations remain drafts;
implementation does not establish effectiveness.

Counts derive from canonical statements. Withdrawn/rejected statements remain
in history but are excluded from usable draft items. Empty and all-abstain
preparation withhold completed review. Supplied positive status strings cannot
replace an executed check.

## Construction, review and verification identities

The four H3 schemas and the independent H3 oracle remain byte-for-byte unchanged.
Canonical UTF-8 hashing, the shared interface hash and raw artifact hashes retain
their distinct domains. Generated JSON uses sorted keys, two-space indentation,
unescaped Unicode and one terminal LF. Original ingress remains separate.

A synthetic draft decision binds the exact construction manifest. It requires
resolved distinct role IDs, declared conflicts and
`issued <= declared evaluation <= current evaluation < expires`. Role IDs do not
authenticate people. A material packet change makes the earlier decision stale;
the old bytes remain intact. Actual authority and substantive approval remain
unverified/not-established.

The H4-specific `heaps-verification-1.0` observation is a later detached receipt.
It binds the raw supplied manifest/status captures, generated manifest, generated
status and explicit observation time. Verification files sit outside the
decision-covered construction inventory. This records exact verification inputs
without inserting a manifest into itself or changing an unchanged construction
merely because it was checked again. H3 input schemas are not extended.

## Boundaries, next stage and rollback

H4.4 D0 byte spans and H4.5 AcciMap composition are intentionally omitted and
unqualified, as permitted by the H4 acceptance plan. Source-check scope remains
`record_reference_integrity` with exact raw artifact bindings. Accepted D0/D1
does not qualify HEAPS composition. Automatic extraction and model work remain
separate.

The supported subset is safe synthetic UTF-8 text, at most 4 MiB per artifact,
32 MiB per packet and 64 JSON nesting levels. Specified calendar assertions use
explicit UTC only. HTTPS metadata and active/sensitive export values remain
outside this runtime subset. Mapped taxonomy declarations require a captured,
available snapshot of the matching identity/version and `taxonomy` purpose;
category fit is not established. Receipt-shaped artifacts use detached channels,
not the construction inventory.

H5 independent qualification/handoff remains a separate phase; H4 regressions
are reusable evidence, not its acceptance declaration. H6 needs the current
authorised local instrument and applicable authority. No clinical review,
official form conformity, external submission, operational deployment, release
or patient benefit is established.

Revert the dedicated H4 consumer/tests/documentation through a normal commit if
needed. Preserve H2/H3 prerequisites, original cases, sources, historical
decisions and failed observations unless their own explicit rollback is intended.
Shared canonical schemas, validators, workbench, CI, dependencies and other
owners' implementations are unchanged by H4.
